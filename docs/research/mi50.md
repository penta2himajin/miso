# AMD Radeon Instinct MI50 (gfx906) — hardware research

Status: recorded 2026-09-25 on the development host. Every number is tagged with its provenance:

- **[DS]** AMD datasheet / official AMD documentation (see [Sources](#sources)).
- **[M]** measured on this host with `bench/mi50/` (raw output in `bench/mi50/results/`).
- **[Q]** queried from the driver / runtime (`rocminfo`, `rocm-smi`, `hipDeviceGetAttribute`, sysfs).
- **[C]** checked by compiling for `--offload-arch=gfx906` and inspecting the emitted ISA (`bench/mi50/isa_probe.sh`).
- **[D]** derived arithmetically from the above.
- **[R]** third-party report, not reproduced here.

## 1. Summary: facts that shape the engine

1. **Decode is HBM-bound, and the achievable ceiling is ~797 GB/s, not 1 TB/s.** Measured streaming read is 78% of the 1024 GB/s peak; write is 61% (623 GB/s). [M]
2. **No matrix cores.** gfx906 has no MFMA and no AGPRs. Dense math goes through packed FP16 (`v_pk_fma_f16`) or the dot-product instructions. [C]
3. **Native integer dot products, including INT4.** `v_dot4_i32_i8` measures 51 TOP/s and `v_dot8_i32_i4` measures 102 TOP/s — 4x and 8x the FP32 rate. [C][M]
4. **No BF16 arithmetic.** `v_dot2_f32_bf16` is not available (needs `dot9-insts`). BF16→FP32 is a single 16-bit shift, so BF16 is a storage format only. [C]
5. **No hardware FP32/FP16 global atomic add.** `atomicAdd(float*)` lowers to a `global_atomic_cmpswap` loop. Split-K / MoE scatter-add must avoid float atomics. [C]
6. **Effective L2 is 4 MiB** (plateau to 4 MiB, falls off at 8 MiB), although `rocminfo`/`hipDeviceProp` report 8 MiB. [DS][M][Q]
7. **The host link on this machine is PCIe 3.0 x4 (~3 GB/s)**, through the Z390 chipset. CPU offload of weights is not viable; model load takes ≥6 s for 18 GB. [Q][M]
8. **Kernel launch costs ~1.25 µs back-to-back; hipGraph is not faster (1.6 µs/node) on ROCm 6.3.4.** With ~500 kernels per decoded token this is ~0.6 ms, comparable to the bandwidth floor. [M]
9. **ROCm support is legacy.** gfx906 has been in maintenance mode since ROCm 6.0; ROCm 7.x official matrices omit it. ROCm 6.3.x is the last line that works out of the box. [DS][R]
10. **Existing engines reach 33–50 tok/s decode** on Qwen3.5-35B-A3B (same architecture as Ornith-1.5-35B-A3B), i.e. roughly 10% of the bandwidth floor derived in §8. [R][D]

## 5. Measured performance [M]

`bench/mi50/microbench.hip`, median of 10 runs, default power profile (`auto`). Raw: `bench/mi50/results/2026-09-25-run2.txt`.

### 5.1 Compute

| Kernel (8 independent chains/lane) | Measured | Theoretical at 1725 MHz [D] | Efficiency |
|---|---|---|---|
| FP32 FMA | 12.71 TFLOP/s | 13.25 | 96% |
| `v_pk_fma_f16` | 25.92 TFLOP/s | 26.50 | 98% |
| `v_dot2_f32_f16` | 25.45 TFLOP/s | 26.50 | 96% |
| `v_dot4_i32_i8` | 51.09 TOP/s | 53.00 | 96% |
| `v_dot8_i32_i4` | 102.41 TOP/s | 106.0 | 97% |

All dot instructions issue at full rate (1 per lane per clock), so INT4 dot doubles the INT8 op rate.

### 5.2 Memory hierarchy

| Level | Working set | Measured read | Notes |
|---|---|---|---|
| LDS (`ds_read_b128`) | 16 KiB/block | 11.99 TB/s | 91% of 128 B/clk/CU [D] |
| L1 vector | 16 KiB | 5.75 TB/s | 87% of 64 B/clk/CU [D]; drops at 32 KiB |
| L2 | 128 KiB – 4 MiB | 1.68–1.75 TB/s | flat plateau |
| L2 → HBM transition | 8 / 16 / 32 MiB | 1.56 / 1.29 / 1.08 TB/s | confirms 4 MiB effective L2 |
| HBM read (1 GiB) | — | **797 GB/s** (4 blocks/CU), 762 GB/s (≥16 blocks/CU) | 78% of 1024 |
| HBM write | — | 623 GB/s | 61% |
| HBM copy (R+W counted) | — | 706 GB/s | 69% |

Read bandwidth is best with *fewer* resident blocks (4 per CU at 256 threads); more blocks lose ~4%.

### 5.3 Host link and launch overhead

| Item | Measured |
|---|---|
| H2D pinned / D2H pinned / H2D pageable (512 MiB) | 3.05 / 3.28 / 3.05 GB/s |
| Empty kernel, back-to-back on a stream | 1.25 µs/kernel |
| hipGraph with 400 empty kernel nodes | 1.60–1.65 µs/node (639–661 µs/graph) |
| Launch + `hipDeviceSynchronize` round trip | 16.0 µs |
| `HIP_FORCE_DEV_KERNARG=1` | no change for empty kernels |

Back-to-back cost by grid size (256-thread workgroups; `results/2026-09-25-launch-grid.txt`). "touch" means each thread reads one float and writes one float, the minimum a dependent kernel does:

| Grid | 1 | 60 | 120 | 240 | 480 | 960 |
|---|---|---|---|---|---|---|
| empty kernel (µs) | 1.28 | 1.45 | 1.63 | 1.98 | 2.68 | 4.07 |
| touch kernel (µs) | 2.99 | 2.99 | 3.09 | 3.24 | 3.53 | 4.38 |

A real decode GEMV adds activation setup and first-access latency on top: ~7 µs for a 0.55 MB launch (ADR_004).

### 5.4 Instruction-issue budget [D]

A wave64 VALU instruction occupies a 16-lane SIMD for 4 cycles, so a CU issues at most 1 wave-instruction per cycle: 60 × 1.725 GHz = 103.5 G wave-instructions/s. At the measured 797 GB/s, a kernel therefore has **~130 wave-instructions per KiB of streamed data**. Example: a Q4_K GEMV row of K = 2048 is 1,152 bytes, so the budget is ~150 instructions per row. The first FP16 GEMV used 150 and was instruction-bound (ADR_004).

## 6. Software stack status

- **ROCm lifecycle [DS]:** ROCm 5.7 was the last fully supported release for gfx906. ROCm 6.0 put MI50 / Radeon Pro VII / Radeon VII into maintenance mode (no new features or performance work). The ROCm 7.2.x compatibility matrix does not list gfx906.
- **ROCm 6.4 regressions [R]:** rocBLAS 6.4.0 shipped without gfx906 TensileLibrary files (ROCm issue #4625); rocSOLVER in 6.4.3 lacks a gfx906 code object. ROCm 6.3.3 works without workarounds.
- **TheRock [R]:** nightly gfx906 builds exist (`rocm.nightlies.amd.com/v2/gfx906/`) but are marked "build passing" only — not sanity-tested or release-ready.
- **This install [Q]:** rocBLAS 6.3.4 ships 156 gfx906 code objects (including INT8 Tensile kernels). hipBLASLt ships **none** for gfx906. MIOpen, RCCL, `rocprof`/`rocprofv2`/`rocprofv3`, `rocgdb`, `hipify` are present.
- **Consequence [D]:** any dependency beyond HIP runtime + rocBLAS is a liability. Hand-written HIP kernels are the only path that is not blocked by vendor support, and they can be pinned to ROCm 6.3.x.

## 8. Implications for Ornith-1.5-35B-A3B

Shapes from `ornith-ai/Ornith-1.5-35B-A3B/config.json`: 40 layers (30 Gated DeltaNet + 10 gated full attention, 3:1), hidden 2048, 256 experts top-8 + 1 shared expert, expert FFN 512, full attention 16 Q heads / 2 KV heads / head_dim 256, DeltaNet 16 K heads / 32 V heads / dim 128, vocab 248,320, untied embeddings, 1 MTP layer.

The shape-based numbers below assume uniform bit widths. For the actual Q4_K_M file (mixed Q4_K / Q6_K / F32), see `docs/research/ornith-q4km-gguf.md`: 1.98 GB of weights per token, floor 379 tok/s at empty context.

### 8.1 Bytes touched per decoded token [D]

| Component | Active params / token |
|---|---|
| Routed (8) + shared (1) experts, 3 × 2048 × 512 each, + router | 28.8 M × 40 = 1,154 M |
| DeltaNet projections (qkv 2048→8192, z 2048→4096, out 4096→2048, a/b) | 33.7 M × 30 = 1,011 M |
| Full attention (q+gate 2048→8192, k/v 2048→512, o 4096→2048) | 27.3 M × 10 = 273 M |
| LM head | 509 M |
| **Total** | **≈2.95 B** |

Non-expert weights are 60% of the per-token traffic. Quantizing only the experts leaves decode dominated by the dense projections.

State and cache traffic:

- DeltaNet recurrent state: 32 heads × 128 × 128 × FP32 = 2 MiB per layer, read and written every token → 126 MB/token.
- Full-attention KV cache (FP16): 10 layers × 2 heads × 256 × (K+V) × 2 B = **20 KiB per context token**. 32k context → 671 MB read per token; 262,144 tokens → 5 GiB total.

### 8.2 Decode floor at 797 GB/s [D]

| Weight format | 0 ctx | 4k ctx | 32k ctx | 128k ctx |
|---|---|---|---|---|
| Uniform ~4.5 bpw (1.66 GB) | 447 tok/s | 427 | 325 | 179 |
| Experts 4.5 bpw, dense 8.5 bpw, head 6.6 bpw (2.43 GB) | 312 tok/s | 302 | 247 | 155 |

These are hard ceilings (100% of measured streaming bandwidth). Launch overhead is up to another ~0.6 ms/token at ~500 kernels × 1.25 µs if not overlapped. The reported 33–50 tok/s (§7) is 10–15% of the floor.

### 8.3 Prefill vs decode are different regimes [D]

Ridge point = peak compute / 797 GB/s: 32 FLOP/B on the FP16 dot path, 64 OP/B on the INT8 dot path. A weight matrix reused by *n* tokens at *b* bytes/param has intensity 2n/b.

| Weight bytes/param | Compute-bound above (FP16 math) | (INT8 math) |
|---|---|---|
| 0.5625 (4.5 bpw) | n ≥ 9 tokens | n ≥ 18 tokens |
| 1.0625 (8.5 bpw) | n ≥ 17 tokens | n ≥ 34 tokens |

- **Decode** (n = 1) and **MTP verification** (n = 2–4) are bandwidth-bound everywhere. Kernel goal: saturate HBM with dequant-in-register GEMV and fused epilogues.
- **Prefill** dense projections cross the ridge at a few dozen tokens. Routed experts see only T/32 tokens each for a chunk of T tokens, so they become compute-bound at chunks of roughly 300–600 tokens. Kernel goal: grouped GEMM on `v_dot2_f32_f16` (≤25 TFLOP/s → ≤4.3k tok/s ceiling at 5.9 GFLOP/token) or `v_dot4_i32_i8` with activation quantization (≤51 TOP/s → ≤8.7k tok/s).
- **DeltaNet**: decode is the recurrent delta-rule update (bandwidth-bound on the 2 MiB state); prefill is the chunked form (intra-chunk matmuls, compute-bound). Different algorithms, not just different tile sizes.
- **Full attention**: decode is split-K flash-decoding over the KV cache; prefill is tiled flash attention in LDS.
- **MTP and MoE interact badly**: *n* tokens touch the union of their routed experts. With uniform routing that is 15.8 distinct experts for n = 2 and 30.5 for n = 4 (vs 8), so expert traffic grows almost linearly. Draft acceptance must beat this cost; real routing correlation is unmeasured.

### 8.4 Capacity [D]

~35 B params at 4.5 bpw ≈ 19–21 GB, plus 5 GiB for a full 262k-token FP16 KV cache, plus 62 MB DeltaNet/conv state per sequence, fits in 32 GB for a single sequence. No virtual memory management (§3), so KV/state pools must be preallocated.

## 9. Not yet measured

- ~~Gap between dependent kernels~~: measured, §5.3 (≈3 µs minimum; ≈7 µs for a real GEMV).
- Grid-wide barrier cost (cooperative launch), needed for the ADR_001 D4 trigger.
- HBM latency (pointer chase) and bandwidth of gathered, non-contiguous expert blocks (~0.5 MB each at 4 bpw).
- Sustained clocks under the 225 W cap during multi-minute runs; effect of `rocm-smi --setperflevel high` (needs root). A prior run on this host (`/home/penta/llm-mi50/NOTES-ubuntu.md`, 2026-09-24) observed thermal throttling: 10× tg512 of a dense 27B model (~4 min) hit 103 °C junction (96 °C mean), sclk fell from 1725 to 1386–1606 MHz, mclk stayed at 1000 MHz, and tg dropped 10%. Benchmark protocol must control for this.
- rocBLAS FP16/INT8 GEMM efficiency on prefill shapes (2048×8192, 512×2048 grouped).
- LDS bank-conflict behaviour for the planned tile layouts; integer atomic throughput.
- Impact of ECC (`sramecc+`) on bandwidth.
